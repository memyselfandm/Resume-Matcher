# Storage transaction boundaries

`Database._write_session()` issues SQLite `BEGIN IMMEDIATE` before reads used by a compound write. This serializes writers across connections and processes. Callers commit the entire operation; a raised exception closes and rolls back the transaction. Ordinary read-only queries remain concurrent under WAL. The configured SQLite busy timeout bounds lock acquisition.

All asynchronous mutations use this write context. Synchronous encrypted-key mutations use `_sync_write_session()` with the same reservation and error translation. SQLite `BUSY`/`LOCKED` errors become `DatabaseBusyError`; public callers receive HTTP 503 with `Retry-After: 1`. Other operational errors retain their original failure behavior.

- Creating a replacement master demotes the old failed/processing master and inserts the replacement in one transaction. The demotion is flushed before the insert to respect the partial unique index, but it is not committed separately. A failed insert preserves the prior master. An actively processing master may be replaced; its in-flight completion targets its original resume ID and must not restore a cached master flag. The old row stays demoted. A ready or pending master is retained when another upload arrives; subsequent designation changes use `set_master_resume()`.
- `create_jobs()` writes an entire job-description batch in one transaction. The upload route validates every trimmed description before invoking it. Validation or storage failure cannot leave a prefix of the batch persisted; successful IDs retain input order.
- Tracker create, move, delete, and bulk operations reserve the writer before counting positions or reading siblings. Position allocation and renumbering therefore share the same serialization boundary. The independent `(job_id, resume_id)` constraint retains deduplication semantics.
- Manual tracker creation extracts missing company/role information before opening the writer, then `create_manual_application()` commits the pasted job, cached company/role and card together. Insert failure, contention or cancellation rolls back both records; no compensating orphan deletion is needed. Existing-job `create_application()` retains its read-only replay path and `(job_id, resume_id)` deduplication.
- Each transition from `saved` to any non-saved status fills a missing `applied_at` date. Existing user-supplied dates and an explicit null in the same individual patch are respected. Moves between non-saved statuses do not refill a manually cleared date or erase a previous date. Returning to `saved` and applying again starts another application transition and fills the date only if still missing. Single and bulk moves use the same rule; no implicit first-application history is stored.

## PostgreSQL backend

With `DATABASE_URL` set, `_write_session()` and `_sync_write_session()` both run `SELECT pg_advisory_xact_lock(POSTGRES_WRITER_LOCK_KEY)` as the first statement instead of `BEGIN IMMEDIATE`. One key serializes every writer, async documents and sync `api_keys` alike, so the invariants above hold unchanged. The lock is released when the transaction commits or rolls back. There is no write-throughput gain; PostgreSQL is offered for durability, backups and remote or shared hosting.

- Both engines are forced to `READ COMMITTED`. Each statement after the lock must see rows committed by the previous writer. Under `REPEATABLE READ` the snapshot would predate the lock.
- Every connection sets `lock_timeout=5s`, the counterpart of SQLite's `busy_timeout`. SQLSTATE `55P03` (lock not available), `40001` (serialization failure) and `40P01` (deadlock) become `DatabaseBusyError` → HTTP 503 with `Retry-After: 1`.
- A synchronous key write waiting behind an async writer can block the event loop for up to `lock_timeout`. This matches SQLite's `busy_timeout` behavior.
- Timestamps are ISO-8601 strings compared lexically. On PostgreSQL those columns use `COLLATE "C"`, so ordering stays byte order whatever the database's default collation. The variant applies to tables created by this code. PostgreSQL support is new, so no earlier PostgreSQL tables exist to convert.
- Read-path audit: the only multi-statement read outside the writer is `get_stats()` (four counts). SQLite never gave it one snapshot either: the driver opens no transaction for SELECT-only sessions, so each statement read the latest commit. It stays informational and unchanged. Reads that feed a write (preview validation, master and tracker reads) already run inside the writer reservation.
- psycopg's async mode does not support Windows' default Proactor event loop. On Windows, run the PostgreSQL backend under Docker or WSL (or a selector event loop); SQLite is unaffected.

Moving data: `uv run python -m app.scripts.migrate_sqlite_to_postgres --database-url postgresql+psycopg://...` copies every table in one PostgreSQL transaction under the writer lock. It then verifies per-table counts and per-row content hashes before committing. It refuses a non-empty target unless `--force` is given. API keys are copied as ciphertext, so keep the same `data/.secret_key`.

Testing on PostgreSQL (opt-in, no CI change): `TEST_DATABASE_URL=postgresql+psycopg://user:pass@host:5432/db uv run pytest`. Each test gets its own schema, selected with `search_path` on both engines and dropped afterwards. The harness adds a 10s connect timeout, TCP keepalives and 60s `statement_timeout` / `idle_in_transaction_session_timeout` to every test connection, so an unreachable or stalled server fails the run instead of hanging it. Tests marked `sqlite_only` exercise SQLite driver behavior and are skipped on that run. `tests/integration/test_postgres_backend.py` (`postgres_only`) holds the PostgreSQL counterparts. For a throwaway server: `docker run --rm -d --name rm-pg -e POSTGRES_PASSWORD=rmtest -p 127.0.0.1:55432:5432 postgres:17`. For the collation test the database's default collation must be linguistic (the image default `en_US.utf8` is), not `C`.

Regression coverage: `tests/integration/test_storage_atomicity.py` injects failures at real ORM inserts, holds allocations while competing writers run, checks shared-file database instances, and exercises API validation with real SQLite. Tests use temporary storage and synthetic content.
